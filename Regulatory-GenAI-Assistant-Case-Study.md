## Executive Summary

This project is a research application over five public Reserve Bank of India (RBI) documents for non-banking financial companies (NBFCs). It turns PDFs into searchable, page-tracked passages; retrieves evidence for an English question; and uses a local Phi-4-mini model to return a cited answer, or to abstain when the evidence doesn't support one. A separate QLoRA experiment adapts the same model family to classify regulatory passages by topic. The system is deployed as a CPU-only demonstration on Google Cloud Run.

The most useful result is not a headline accuracy number. It is a measurement framework honest enough to show where the system is weak. On a frozen 40-question development set, the recorded baseline retrieved the reference passages for 58% of cases and **abstained far too often** (32 of 35 completed responses). The evaluation also exposed false language rejections, slow responses and timeouts. The classifier experiment showed a clearer gain: a QLoRA adapter lifted agreement with document-derived labels from 34% (unadapted base) to 82% on a small validation set, with an important caveat that those labels were not human-reviewed. Human-reviewed answer accuracy, applicability of the rules over time, and the reserved test sets remain open work, and this case study says so throughout.

## 1. Background and Problem

Regulatory documents are long, cross-referenced and revised. A user asking "what are the main components of an NBFC's KYC policy?" needs an answer that can be traced to a page of a specific document, and needs the system to say so when it cannot answer. A fluent but unsupported answer is worse than no answer in this domain.

Three problems shaped the design:
1. **Identity of the source.** Files named `kyc.pdf` and `kyc-final.pdf` don't establish which bytes, version or organization an answer came from.
2. **Grounding.** A small local model can invent citations, ignore conditions or answer outside its evidence.
3. **Knowing how well it works.** A demo that works on one question says little about how often it fails, so evaluation had to be built before any quality claim.

The project deliberately does not claim to determine which rule is legally in force today. The source inventory has no reviewed applicability intervals, so questions that require current-law determination are meant to be withheld.

## 2. Design Philosophy

- **Evidence over eloquence.** The model sees only selected, eligible passages. Provenance fields such as titles, page numbers and hashes are copied by the application from stored inputs, never generated by the model.
- **Abstention is a result, not an error.** "The evidence doesn't support an answer" is tracked separately from timeouts and service failures, so neither can hide inside the other.
- **Measure before claiming.** Questions were frozen before the baseline was observed. A reserved test split is not touched until references are human-reviewed. Draft references and weak labels are labeled as such in every result.
- **Everything is versioned and inspectable.** Source hashes, corpus version, embedding identity, prompt version and generator identity are recorded, and a saved index is rejected if its inputs have changed.
- **Say what a number means.** Agreement with weak labels is not accuracy, and citation membership is not semantic support.

## 3. Architecture

### Phase 1: source identity and audit
A manifest lists each document with its hash, title, regulator, topic, entity type, issue and revision dates, status and verification state. A read-only audit command checks that the files on disk match the recorded bytes and that the manifest and configuration are valid, and it reports exact duplicates. Metadata review is kept separate from file integrity: a document can pass the hash check while its applicability is still unresolved. Unknown values stay `null` and are never guessed.

### Phase 2: from PDFs to searchable passages
- **Extraction and cleaning:** page-aware text extraction, with conservative cleaning that preserves raw text and removes only recognized noise.
- **Chunking:** section-aware passages of up to 350 words with a 50-word overlap, each carrying its document ID, physical page range and source hash.
- **Embedding and index:** `all-MiniLM-L6-v2` (384 dimensions) on CPU, pinned to an exact model revision. Passages longer than the model's input limit are covered by overlapping 224-token windows, then pooled, so no text is silently dropped. Vectors are stored in a FAISS inner-product index over normalized vectors (cosine similarity), and the index is rejected when the corpus, embedding code or package versions change.
- **Result:** 5 documents, 251 physical pages, 359 passages.

### Phase 3: guarded, cited answers
A request passes through up to five model calls, with early exits when a gate fails:
1. **Language check**, since the system accepts English only.
2. **Scope check**, for example rejecting "what is the weather?" and questions that require current-law applicability.
3. **Evidence retrieval and selection**, restricted to eligible NBFC sources and excluding withdrawn ones. The selector counts the complete prompt with the model's own tokenizer against a budget of 4,096 tokens minus reserved output and safety margin, keeping whole passages in rank order.
4. **Evidence review**, which asks whether the selected passages support the whole question, including conditions and exceptions, and answers `supported`, `insufficient_evidence`, `ambiguous` or `conflicting_evidence`.
5. **Generation** into a constrained JSON contract (answer, citations, abstain, reason), where citation IDs are limited to the supplied passages and validated again after parsing, followed by a **claims review** that checks the answer against only the passages it cited and can replace it with an abstention.

Operational safeguards include a 16 KiB request limit, strict request validation, a spawned child process per request with a deadline, and limits of one active request and six admissions per minute per server process. The same local model performs generation and both reviews, so the reviews can share its errors. They are not independent human validation.

### Phase 4: evaluation
- A frozen set of 40 development and 20 reserved test questions, covering single and multiple passages, multiple documents, historical-change uncertainty, unanswerable questions, wrong entity, ambiguity, out-of-scope requests and prompt injection.
- Retrieval is scored separately from integrated answers (Recall@k, MRR@k), alongside abstention precision and recall, citation membership, reference coverage, latency and token usage.
- Runs are fingerprinted so an interrupted run can resume only if nothing relevant has changed, and operational failures are retained rather than retried until they disappear.
- A human-review path exists, scored from named reviewers' judgments. At the time of writing, zero references and zero answers have been human-reviewed.

### Phase 5: a QLoRA classification experiment
Phi was adapted to classify a passage into one of five topics (KYC, lending, customer conduct, outsourcing, grievance redressal). This is a separate route from the answering pipeline and does not improve its answers.
- **Data:** 359 passages with labels derived from each source document, split by four-page blocks to avoid near-duplicate leakage between training and evaluation: 190 train, 38 validation, 45 reserved test (unused), 86 excluded.
- **Training:** QLoRA on a Colab T4 GPU. The checkpoint with the lowest validation loss (epoch 2) was selected, and the adapter was about 44 MiB.
- **Serving:** the adapter was merged into the base model, converted to GGUF and quantized (Q4_K_M, about 2.3 GiB) so the classifier runs on CPU through Ollama.

### Serving and delivery
FastAPI exposes the question endpoint, a classification endpoint, health and readiness checks, and a same-origin browser interface. The demonstration runs on Google Cloud Run on CPU only with concurrency one, long request timeouts, and a workflow that starts and stops the service so it is active only during demos. GitHub Actions runs structure, lint, formatting and test checks on every push.

## 4. Results

### Corpus and index
| Item | Value |
|---|---|
| Documents | 5 (KYC, responsible business conduct, credit facilities, outsourcing, internal ombudsman) |
| Physical pages / passages | 251 / 359 |
| Embedding dimensions | 384 |
| Source file audit | 5 of 5 hashes match, no duplicates |

### Development baseline for the answering pipeline
Recorded on the 40 development questions against an earlier, larger corpus and the then-current configuration, with draft references and no human review:

| Observation | Result |
|---|---|
| Recall@3 and Recall@5 (24 cases with reference passages) | 0.583 each |
| MRR@3 and MRR@5 | 0.542 each |
| Completed responses / operational errors | 35 / 5 (three service-unavailable, two timeouts) |
| Completed responses that answered / abstained | 3 / 32 |
| Abstention precision / recall (draft labels) | 0.50 / 1.00 |
| Abstain-or-answer agreement with draft labels | 19 of 35 completed (54%); 19 of 40 counting failures |
| Citation membership | 9 of 9 cited IDs belonged to the selected evidence |
| Mean reference-passage citation coverage | 0.158 |
| Mean / 95th-percentile elapsed time per attempt | 41.4 s / 132.8 s |
| Human correctness | not measured |

Two timeout attempts took 200.5 s and 633.5 s despite a 180-second deadline. The report keeps those observations and doesn't claim a cause. The recorded issue register named false English-language rejections and document-specific questions wrongly treated as requiring a current-law determination.

A separate authenticated smoke test on the CPU-only cloud demo answered "what is KYC?" with a supported answer citing the expected KYC policy passage, in about 378 seconds, which is too slow for an interactive demo and is the main reason a short cloud session is inconvenient.

### Classifier experiment
Agreement with document-derived (weak) labels on 38 validation passages. These are not human-reviewed labels, so none of these numbers is accuracy:

| Method | Agreement | Macro-F1 |
|---|---|---|
| Majority label | 10 / 38 (26%) | 0.083 |
| Keyword rules | 22 / 38 (58%) | 0.557 |
| Five-shot Phi through Ollama (earlier protocol) | 27 / 38 (71%) | 0.651 |
| Base model, NF4, adapter off (matched test) | 13 / 38 (34%) | 0.411 |
| Base model, NF4, adapter on (matched test) | 31 / 38 (82%) | 0.806 |
| Merged, quantized, on CPU | 29 / 38 (76%) | 0.730 |

Part of the adapter's gain came from returning a valid label more reliably: the unadapted base produced 18 invalid or failed outputs. The CPU model recovered only 2 of 9 customer-conduct passages, so that label should not be used alone to gate retrieval.

## 5. What the Measurements Show

1. **The pipeline is safe but not yet useful on answerable questions.** Its guardrails held, since every citation referred to selected evidence, but it abstained on most questions it should have answered. Explicit separation of "abstained" from "failed" is what made the problem visible.
2. **Citation membership is a weak quality signal.** 100% valid citation IDs coexisted with low coverage of the reference passages and no measure of semantic support.
3. **Retrieval is the first limit.** With Recall@5 near 0.58 against draft references, a better answer model cannot recover passages that were never retrieved. Some misses may be reference gaps, so each needs inspection.
4. **Reproducibility needs more than saved weights.** A reloaded adapter initially matched only 30 of 38 weak labels and reproduced 37 of 38 predictions because non-quantized parameters were in a different precision than during training. Applying the same preparation restored all 38 original predictions.
5. **Latency dominates the demo.** On CPU, a fully reviewed answer needs several model calls and took minutes.

## 6. Key Engineering Decisions

| Decision | Alternative | Why |
|---|---|---|
| Hash-verified manifest as the source of truth | Trust file names | Results can be traced to exact source bytes |
| Passages carry document, page and hash | Plain text chunks | Citations can be traced to a page |
| Application attaches provenance | Ask the model for titles and pages | Generated provenance is fallible |
| Abstention separate from failure | One "no answer" outcome | Each needs a different fix |
| Per-request child process with deadlines | In-process thread | A blocked call can be bounded and terminated |
| Complete-prompt token budgeting | Count only passage text | Instructions and metadata use context |
| Frozen questions, reserved test split | Tune on all questions | Avoids evaluation leakage |
| Page-block split for classification | Random split of overlapping chunks | Near-duplicate chunks would inflate scores |
| CPU-only, scale-to-zero demo | Always-on GPU hosting | Fits a portfolio budget and demo-only use |

## 8. Testing and Verification

The full regression suite had **448 passing tests** when the project guide was last verified, including 71 focused on ingestion and indexing and 48 on the source audit and configuration. Tests use synthetic inputs, deterministic embedders and temporary directories, and they cover corrupt or encrypted PDFs, tampered or stale artifacts, citation membership, timeouts and abstention paths. They establish contracts and boundaries. They do not establish retrieval quality or answer correctness, which the evaluation measures separately.

## 9. What This Project Demonstrates

- **Evaluation discipline:** frozen questions, a held-out split, fingerprinted resumable runs, and results reported with their denominators and caveats, including the unflattering ones.
- **Guarded generation:** schema-constrained output, citation validation, claim review, application-owned provenance, and explicit abstention.
- **Full-stack ML delivery:** from PDF parsing and embeddings through QLoRA fine-tuning, GGUF export and CPU serving to a cloud-hosted demo with CI.
- **Reproducibility habits from a QA background:** integrity checks, contract tests, failure-boundary testing, and refusal to let a pass on one check stand in for another.
